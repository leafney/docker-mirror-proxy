# dmp pull 无进展超时优化讨论

## 原始需求

用户在执行 `dmp pull rabbitmq:4.3.1-management` 拉取 Docker 镜像时发现，当前默认超时时间为 60 秒。部分 Docker 镜像总下载时间会超过 60 秒，但下载过程仍在正常进行。当前实现把 60 秒作为整个 `docker pull` 的总耗时上限，导致正在下载的镜像被停止，然后切换到下一个加速地址。

用户希望针对这种问题思考并给出优化建议。

## 代码现状

- `internal/app/app.go` 对每个候选镜像地址使用 `context.WithTimeout(ctx, opts.Timeout)`。
- `internal/docker/client.go` 使用 `exec.CommandContext(ctx, "docker", args...)` 执行 Docker 命令。
- 因此 `--timeout` 当前实际含义是单个候选地址的总耗时上限。
- 当前行为无法区分“仍在下载但总耗时较长”和“长时间无响应卡住”。

## 问答记录

### 问题一

`--timeout 60` 以后代表哪种含义？

推荐答案：代表“无进展 60 秒超时”，不是“总耗时 60 秒超时”。这样最符合当前用户直觉，也最能解决大镜像下载被误杀问题。

用户答案：同意，代表“无进展 60 秒超时”。

### 问题二

什么算“有进展”？

推荐答案：先用“Docker 命令有任何 stdout/stderr 输出”当作有进展。实现简单，风险低，不需要复杂解析 `Downloading 13.8MB`、`Pull complete` 等状态。

用户答案：同意。

### 问题三

是否新增“总耗时上限”参数？

推荐答案：新增 `--max-time`，默认 `0`，表示不限制总耗时。`--timeout` 解决无进展卡住，`--max-time` 解决有输出但一直拖很久的极端情况。

用户答案：同意。

### 问题四

`docker pull` 直接报错时，要不要继续按现在逻辑切下一个源？

推荐答案：保持现状，任何 `docker pull` 非零退出都切下一个源。`unknown blob`、`manifest unknown`、网络断开等错误不做复杂分类。

用户答案：同意。

### 问题五

`--max-time` 短参数是否使用 `-m`？

推荐答案：使用 `-m`。Cobra/pflag 短参数通常是单字符，`-mt` 容易被解析成 `-m -t`，不推荐为它增加自定义预处理。

用户答案：同意。

## 最终共识

- `-t, --timeout` 表示无进展超时，默认 60 秒。
- 只要 `docker pull` 的 stdout 或 stderr 有输出，就视为仍有进展，并刷新无进展计时。
- 新增 `-m, --max-time` 表示单个候选地址的总耗时上限，默认 0，表示不限总耗时。
- `docker pull` 非零退出仍按现有逻辑切换下一个候选加速地址。
- 日志需要区分普通失败、无进展超时、总耗时超时。
- 文档需要更新 `--timeout` 的语义，避免用户误以为它仍是总耗时上限。
